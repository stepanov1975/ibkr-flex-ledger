# Corporate-action resolutions implementation plan

Goal: Implement the approved actionable review flow for paired identifier changes and security distributions, preserving broker evidence and independent accounting uncertainty.

Design: Keep immutable broker rows. Read every leg sharing the current action's broker artifact and action ID. Offer a source-bound security transfer for a validated equal-quantity IC pair, and a distribution opening with explicitly supplied total cost basis for a single credited SO security. Save the chosen treatment in a separate resolution record. Preview by rebuilding historical snapshots and lots in a rolled-back transaction; apply repeats the calculation and checks an exact input fingerprint under the ingestion lock. Identical replay preserves approved treatments; changed legs invalidate them. Complex mergers, basis allocations out of a parent, cash elections and unverified security remapping remain unsupported, separately counted and explained.

Accounting choices require the operator's explicit preview and apply decision.

1. Ledger movements: Add dated full-position transfers and distribution openings; carry FIFO basis/acquisition dates across identities, retain past realized P&L on the source, and persist corporate-action opening lots without invented trades. Verify seeded transfers, later sales, distributions including explicit zero basis, scoped rebuilds and replay.
2. Resolution backend: Group broker legs by artifact/action ID. Add additive resolution/lot migration, evidence and resolution options to case API, rollback-only preview and atomic apply. Verify stale previews, source changes, replay, invalid quantities and account locking.
3. Review UI: Count only available decisions; separate unsupported accounting; show actual broker legs and exact missing facts; add transfer and distribution editors with Preview/Apply/Cancel, before/after snapshots and lots. Preserve split controls. Execute shipped JS for transitions and failure handling.
4. Integration: Run full pytest against isolated PostgreSQL databases, Ruff and MyPy; independent review; build/restart the local app, check health and live rollback-only previews without applying a correction.

Interfaces: LedgerSecurityMovementRecord contains event_corp_action_id, source_raw_record_id, source_instrument_id (nullable), destination_instrument_id, report_date_local, quantity, cost_basis (nullable), currency. SQLAlchemyLedgerSnapshotService.db_ledger_security_movement_list_for_account reads active resolutions via app.db.corporate_action_resolution.read_security_movements(connection, account_id, through_report_date_local). Security transfer has source and no entered basis; distribution has no source and an explicit nonnegative basis. Movement currency is the action currency. API cases expose review_state (actionable/unsupported/handled), resolution_options [{type,label}], broker_legs [{symbol,conid,quantity,currency,cost_basis,report_date_local,description}], review_reason and required_check. POST /cases/{id}/resolution/preview|apply accepts treatment, note, optional cost_basis, and on apply preview_token. Results have case_id, treatment, summary, snapshots [{symbol,report_date_local,currency,before,after}], lots_before/lots_after [{symbol,remaining_quantity,cost_basis_remaining,opened_at_utc}], preview_token, applied.

Original distribution origins plus transfer lineage produce distinct deterministic lot IDs, including round trips. Rebuilds process connected holdings while persisting each existing snapshot with its original valuation context. An approved full transfer that becomes ineligible after new historical activity is deactivated and moved to unsupported accounting with its specific reason; the import still commits.
