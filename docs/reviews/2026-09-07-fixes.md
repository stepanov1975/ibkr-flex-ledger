## Applying to an existing installation

1. Take and verify a database backup using the existing operations procedure.
2. Build and restart the application with the updated code and requirements. Preserve the
   published LAN port used by the existing installation.
3. Replay retained successful artifact scopes in chronological report-date order. Use the
   replay-only HTTP endpoint `POST /ingestion/reprocess?period_key=YYYY-MM-DD&flex_query_id=QUERY`
   through the trusted local/proxy boundary. Repeat for every historical scope requiring repair.
   Ordinary exact-duplicate ingestion can still skip an already-completed artifact when the
   account has no failure history, so deploying code alone does not repair stored snapshots.
4. Verify historical FX coverage, positions, cost basis, P&L, reconciliation, and manual cases
   against broker records. Previously accepted CASHDIV rows become manual cases on replay;
   confirm that their payment/withholding is represented in CashTransactions before resolving.
5. Schedule the updated backup script through the existing maintenance lock. It runs WAL
   cleanup only after successful backup verification and daily-backup retention.

No production replay, database cleanup, alert delivery, or service restart was performed as
part of source development and regression testing.

## Deliberate limits and tradeoffs

- Failure invalidation uses durable run status and survives diagnostics retention. It is
  account-wide and conservative: even fetch-only failures disable the optimization. Do not
  delete audit history to re-enable skips. This favors correctness over incremental speed.
- A successful subsequent partial report remaps the rows it contains; it does not atomically
  roll back a previous failed import's entirely new events or rebuild dates outside its scope.
  Historical investigation/replay is still required for previously corrupted data.
- CASHDIV is manual because the source currently lacks an unambiguous cross-section cash
  identity contract. This corrects silent acceptance; it does not add speculative cashflows.
- Partial SMTP retry can redeliver to recipients who already accepted the same event ID.
- WAL is retained from the oldest daily baseline. Older weekly/monthly backups contain
  consistency WAL and remain restorable at backup completion, but do not guarantee continuous
  PITR from those older dates. Cleanup follows PostgreSQL's
  [pg_archivecleanup boundary semantics](https://www.postgresql.org/docs/17/pgarchivecleanup.html).
- Installed tooling/transitive packages reported by the review audit are updated through
  explicit pins: Click, Mako, pip, Pygments and setuptools. The Mako fix version is documented
  in the [maintainer advisory](https://github.com/sqlalchemy/mako/security/advisories/GHSA-2h4p-vjrc-8xpq).
